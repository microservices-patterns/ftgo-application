HOLONIC SEMANTIC CHANGE REVIEW
Customer and AI-assisted evaluation guide

PURPOSE

One tool reviews a code change in context: what it preserves, what it changes,
what impact it may have, and whether it conflicts with accepted expectations
or introduces a potential defect.

It is a governor and review aid, not a replacement for testing or human judgment.
In this evaluation it is advisory: it records findings and decisions but does not
block a merge.
Intentional changes can still conflict with project expectations. A clean result
does not prove that the entire application is correct.

WHAT TO EXPECT

Focused changes with clear project expectations are the best starting point.
The review can identify supported behavior-preserving changes, unexpected
consequences, compatibility concerns, and potential programming defects.

Findings, investigation items, and requests for an owner decision are parts of
the same assessment. Read them alongside the evidence and reported coverage.
An investigation item is a reason to review, not a declaration that code is broken.

The project's accepted expectations determine what can be treated as a governed
violation. Other potential defects can also be surfaced within the review's scope.
Do not assume that every behavior or every repository file has been assessed.

Findings fall into two broad kinds: a change in behavior relative to the accepted
baseline, and a conflict with an accepted constraint, including in code the PR
did not touch. The review can also point out questionable tests, such as tests
that only assert their own expected answer.

The accepted expectations for this evaluation were prepared in advance. Authoring
or editing them directly is not part of this evaluation.

KNOWN LIMITS

Do not expect every bug to be found or every refactor to be recognized.
Complex interactions, missing context, unfamiliar environments, and large
rewrites may require human review or produce an incomplete assessment.

The tool does not prove arbitrary program equivalence or fully predict production
behavior. It reviews code without observing production execution. It can flag
code defects that would cause runtime failures, but cannot establish failures
that depend on unavailable production data, configuration, or external behavior.
Keep normal tests and security review. Confirm the release and review
configuration before comparing results or running a customer demonstration.

This evaluation focuses on one repository. Do not assume that dependent
repositories are also covered. The review can assess integration code and
available contract information, but cannot verify the behavior of an external
service whose implementation or runtime evidence is unavailable. Such limits
should be reported rather than guessed. Confirm the accepted baseline used for
the comparison; changes that reach main outside the reviewed process can leave
it out of step.

ROUGH PERFORMANCE GUIDANCE

These rounded figures describe small Java-focused development evaluations used
during improvement. They are orientation, not independent customer certification,
confidence intervals, or guarantees for another project or the deployed service.

Known bugs flagged for review, approximately:

  Loops                  85%
  Recursion              90%
  Memory retention       75%
  Resource leaks         95%
  Null safety            85%
  Value equality         90%
  Deadlocks              40%
  Races                  90%
  Cache correctness      90-95%

Overall, roughly 80-85% of known bugs were flagged in those evaluations.
A flag includes either a finding or an investigation item; it does not necessarily
mean a blocking result or a confirmed runtime failure.

Roughly 10-15% of known-safe changes also received a review flag. That is a
safe-change flag rate, not overall accuracy. Noise varies by category: cache
examples approached one safe change flagged in three. Deadlock coverage was
comparatively weak, and difficult loop behavior remains challenging.

Some cases were not fully assessed. Unflagged and incomplete cases must not be
treated as verified safe. Small samples and variation between runs mean these
numbers should not be read as precise forecasts.

CHANGE SIZE

Start with focused PRs. A few hundred changed lines can make a useful demonstration,
but line count alone does not determine review quality. Split unrelated changes
and significant rewrites where practical. Check reported coverage before drawing
conclusions from a large PR; successful submission does not guarantee full analysis.

READING THE ASSESSMENT

  No finding: No issue was identified within the assessed scope, not a safety
  certificate for the change or the application.

  Investigation: A specific potential issue needs review and may be a false alarm.

  Owner decision: The change affects an accepted expectation or needs an explicit
  decision about newly introduced behavior.

  Incomplete: The available evidence does not support a conclusion. This is
  neither a confirmed defect nor a pass.

Recording a decision on a PR does not establish correctness. An accepted change
can become part of the baseline after the PR merges to main and the configured
acceptance and baseline-update process succeeds. Recording approval alone does
not guarantee that update; confirm the resulting baseline before expecting
later reviews to use it. Declining leaves the item recorded as unresolved.
False-alarm feedback can inform later reviews, but does not guarantee that
similar findings will never recur or that an exception has been applied.

Plain-language summaries are generated from the underlying evidence. Check them
against the before and after evidence and the code change.

GUIDANCE FOR AN AI ASSISTANT

- Read the project's expectations and the assessment before asking broad questions.
- Compare results using the same release, configuration, and accepted baseline.
- Use realistic changes and include safe controls, not only deliberately broken code.
- Keep expected verdicts outside the inputs being reviewed; do not plant test hints.
- Check whether a finding matches the actual change, not merely a nearby issue.
- Report catches, misses, safe-code flags, and incomplete cases distinctly.
- Count each test case once, even if the assessment contains several messages.
- Ask specific questions only when the supplied information cannot answer them.
- Do not automatically approve findings, merge PRs, change accepted expectations,
  or rewrite intentional behavior.
- Do not claim product-wide success or failure from one example.
- Do not record decisions or merge on the owner's behalf. Confirm completion
  of the accepted baseline-update process before treating a decision as the
  basis for later PR comparisons.

SUGGESTED SEMANTIC PR TYPES

Use the same unified review for each scenario. These are evaluation targets,
not promises that every example will produce a particular result.

1. SAME BEHAVIOR
   Reorganize a real workflow without changing its outcomes or obligations.
   Look for preserved behavior without an invented violation. Include a cosmetic
   change as a simple control; use a substantive refactor for the main example.

2. UNINTENDED CONSEQUENCE
   Make a plausible change that causes an unexpected effect elsewhere.
   Look for a relevant impact or investigation item, not an unrelated warning.

3. INTENTIONAL BEHAVIOR CHANGE
   Deliberately alter an existing business policy while keeping implementation
   internally consistent. Look for the changed expectation and any owner decision.
   Intentional does not mean automatically accepted.

4. COMPATIBILITY CHANGE
   Change an interaction between components. Compare an incompatible change
   with a coordinated update, using the project's actual expectations.

5. RELIABILITY REGRESSION
   Introduce a realistic failure in an existing workflow. Pair it with a similar
   safe change. Look for the correct issue and measure unnecessary review flags.

6. LARGER REFACTOR
   Compare one larger behavior-preserving change with the same work split into
   focused PRs. Look for honest coverage reporting, not blanket approval.

7. NEW FEATURE
   Add a new capability or API alongside existing workflows. Look for the new
   behavior to be surfaced for an owner decision, and for any effect on existing
   expectations to be reported separately.

Keep one main hypothesis per PR. Maintain a private evaluator answer sheet with
the expected behavior and a concrete explanation of each defect. Preserve the
evaluated commits until review is complete, and do not merge deliberately broken
demonstrations into the accepted baseline.

This guide describes customer-visible expectations and limitations. Proprietary
implementation details are intentionally omitted.
