= FTGO: Workflow-Based Semantic Change Review
:toc:
:toclevels: 2

FTGO is a food-ordering application built from collaborating services.
Holonic reviews its pull requests against accepted expectations for those
services and the workflows they implement.

The review connects a code change to a business question: does this order still
carry the right identity and amount, can a cancellation still be undone, and do
the participating services still follow the agreed sequence?

== How a pull request is gated

Opening or updating a pull request to `master` starts
link:.github/workflows/codeintent-checks.yml[CodeIntent Checks].
The workflow submits the change to the review service, which compares it with
the application's accepted baseline and publishes a result on the PR.

The review brings together:

* *Source evidence:* changes to calls, values, state transitions, endpoints,
  and service coordination.
* *Workflow expectations:* accepted obligations bound to the affected code.
* *Assessment:* whether the evidence supports preservation, a conflict with an
  obligation, an owner decision about changed behavior, or further investigation.
* *Explanation:* a plain-language account of the recorded evidence and its
  relationship to the workflow.

A behavior-preserving change is assessed against the same obligations as a
behavior-changing one. Changes to an accepted obligation are brought forward
for review; new or unbound behavior is presented for an owner decision.
When evidence is incomplete, the report keeps that state explicit and can
include a separately labeled advisory LLM review.

The gate publishes check and review status. GitHub's configured branch rules
control merge enforcement. Reviewers use the PR's live report to inspect the
before-and-after evidence and record the appropriate decision. An accepted
change becomes the comparison baseline through the configured post-merge
baseline-update process.

== Customer order lifecycle

=== Place an order

*Business purpose:* carry a customer's order through validation, kitchen ticket
creation, payment authorization, and approval.

*Accepted gate check:* the authorization command takes its consumer identity
and total from the order details, and its order identity from the saga state.
This connects the payment request to the order being processed.

*Changes brought to review:* substituting another consumer, using a different
order ID, or changing the amount supplied to authorization.

Binding: `place.authorize_order`.
Source: link:ftgo-order-service/src/main/java/net/chrisrichardson/ftgo/orderservice/sagas/createorder/CreateOrderSagaState.java[CreateOrderSagaState].
The participant sequence is governed separately under <<create-coordination>>.

=== Cancel an order

*Business purpose:* coordinate cancellation across the order, kitchen, and
accounting services, including recovery when a forward step is undone.

*Accepted gate checks:*

* The cancellation endpoint passes the requested `orderId` unchanged to
  `orderService.cancel` (`cancel.accept_request`).
* Kitchen cancellation accepts `ACCEPTED` or `AWAITING_ACCEPTANCE` tickets,
  saves the prior state, and enters `CANCEL_PENDING` (`cancel.begin_ticket`).
* Order compensation returns an order from `CANCEL_PENDING` to `APPROVED`
  (`cancel.compensate_order`).
* Ticket compensation restores the ticket's saved previous state
  (`cancel.compensate_ticket`).
* The ordered confirmation phase routes ticket and order confirmation to
  their respective `CANCELLED` transitions (`cancel.confirm`).
* Authorization reversal is dispatched to accounting and routed to
  `accountRepository.update` (`cancel.request_authorization_reversal`).

*Changes brought to review:* changing the cancellation target, accepting a
new ticket state, dropping a saved state or undo step, redirecting reversal,
or changing the confirmation transitions.

=== Revise an order

*Business purpose:* start a coordinated update to an existing approved order.

*Accepted gate check:* beginning a revision accepts an `APPROVED` order,
changes it to `REVISION_PENDING`, and returns an `OrderRevisionProposed` event
carrying the calculated totals.

*Changes brought to review:* allowing revision from another state, changing
the pending state, or changing the totals carried by the proposal event.

Binding: `revise.begin_order`.
Source: link:ftgo-order-service/src/main/java/net/chrisrichardson/ftgo/orderservice/domain/Order.java[Order].
The participant sequence is governed separately under <<revise-coordination>>.

=== View an order

*Business purpose:* retrieve the order requested by a customer.

*Accepted gate check:* the query endpoint looks up the requested identity and
distinguishes a successful response from an order-not-found response.

*Changes brought to review:* looking up another identity or changing how a
missing order is represented to the caller.

Binding: `view.read_order`.
Source: link:ftgo-order-service/src/main/java/net/chrisrichardson/ftgo/orderservice/web/OrderController.java[OrderController].

== Fulfillment operations

=== Fulfill a kitchen ticket

*Business purpose:* move kitchen work from acceptance through preparation and pickup.

*Accepted gate checks:* an accepted ticket can enter preparation
(`kitchen.prepare_ticket`), and a ready ticket can record pickup
(`kitchen.pickup_ticket`).

*Changes brought to review:* changing the states that permit preparation or
pickup, or changing the resulting transitions.

Source: link:ftgo-kitchen-service/src/main/java/net/chrisrichardson/ftgo/kitchenservice/domain/Ticket.java[Ticket].

=== Fulfill a delivery

*Business purpose:* schedule the pickup and drop-off work for an order.

*Accepted gate check:* scheduling loads the requested delivery and available
couriers before appending pickup and drop-off actions.

*Changes brought to review:* loading the wrong delivery, changing courier
selection inputs, or removing or reordering the scheduling actions.

Binding: `delivery.schedule`.
Source: link:ftgo-delivery-service/src/main/java/net/chrisrichardson/ftgo/deliveryservice/domain/DeliveryService.java[DeliveryService].

== Participant operations

=== Manage a consumer

*Business purpose:* create a consumer from the submitted registration details.

*Accepted gate check:* `POST /consumers` passes the supplied request name to
`consumerService.create`.

*Changes brought to review:* dropping, replacing, or transforming the name
passed from the request into consumer creation.

Binding: `consumer.create`.
Source: link:ftgo-consumer-service/src/main/java/net/chrisrichardson/ftgo/consumerservice/web/ConsumerController.java[ConsumerController].

=== Manage a restaurant and menu

*Business purpose:* make restaurant information available to the services
participating in fulfillment.

*Accepted gate check:* a restaurant-created event calls
`deliveryService.createRestaurant` with the event's aggregate identity,
restaurant name, and address.

*Changes brought to review:* changing which event values supply the restaurant
identity, name, or address used by delivery.

Binding: `restaurant.propagate`.
Source: link:ftgo-delivery-service/src/main/java/net/chrisrichardson/ftgo/deliveryservice/messaging/DeliveryMessageHandlers.java[DeliveryMessageHandlers].

=== Manage order authorization

*Business purpose:* process the accounting participant's authorization request.

*Accepted gate check:* authorization updates the account repository using the
command's consumer identity and maps `AccountDisabledException` to
`AccountDisabledReply`.

*Changes brought to review:* using another consumer identity, redirecting the
repository operation, or changing the disabled-account reply.

Binding: `accounting.authorize`.
Source: link:ftgo-accounting-service/src/main/java/net/chrisrichardson/ftgo/accountingservice/messaging/AccountingServiceCommandHandler.java[AccountingServiceCommandHandler].

== Read models and propagation

=== Project order history

*Business purpose:* reflect order progress in the order-history read model.

*Accepted gate check:* an order-authorized event updates the matching history
aggregate to `APPROVED` and retains source-event evidence.

*Changes brought to review:* updating the wrong aggregate, selecting another
state, or dropping the association with the source event.

Binding: `history.update_state`.
Source: link:ftgo-order-history-service/src/main/java/net/chrisrichardson/ftgo/cqrs/orderhistory/messaging/OrderHistoryEventHandlers.java[OrderHistoryEventHandlers].

== Saga coordination

The saga gates review the declared order of cross-service participants.
They connect the individual service operations into the accepted workflow.

[[create-coordination]]
=== Coordinate order creation

*Accepted sequence:* consumer validation -> ticket creation -> accounting
authorization -> ticket confirmation -> order approval.

*Changes brought to review:* removing, replacing, or reordering these forward
participants.

Binding: `create_saga.forward`.
Source: link:ftgo-order-service/src/main/java/net/chrisrichardson/ftgo/orderservice/sagas/createorder/CreateOrderSaga.java[CreateOrderSaga].

=== Coordinate order cancellation

*Accepted sequence:* order cancellation -> ticket cancellation -> authorization
reversal -> ticket confirmation -> order confirmation.

*Changes brought to review:* removing, replacing, or reordering these forward
participants. The cancellation workflow above also describes its compensation
and confirmation obligations.

Binding: `cancel_saga.forward`.
Source: link:ftgo-order-service/src/main/java/net/chrisrichardson/ftgo/orderservice/sagas/cancelorder/CancelOrderSaga.java[CancelOrderSaga].

=== Coordinate order revision

*Accepted sequence:* order revision -> ticket revision -> authorization
revision -> ticket confirmation -> order confirmation.

*Changes brought to review:* removing, replacing, or reordering these forward
participants.

== Working with the review

. Make a focused change to an existing workflow and open a PR to `master`.
. Follow the CodeIntent PR comment to the live report.
. Inspect the affected workflow, its accepted obligation, the source evidence,
  and the explanation together.
. Correct unintended changes, or use the review controls to record an intentional
  change for the appropriate owner decision.
. After an approved merge, confirm the accepted baseline update before comparing
  subsequent changes against it.

For evaluation, pair a behavior-changing PR with a behavior-preserving version
of the same work. Keep expected results outside the submitted PR, including
its branch name, and compare the actual finding with the specific change.
